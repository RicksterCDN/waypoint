# Ledgerfield demo data

This folder contains fictional data, source documents, and scenario metadata for the Waypoint contract manufacturing invoice assurance demo.

## Folder layout

```text
data/
├── suppliers/
│   └── suppliers.json
├── contracts/
│   ├── source-markdown/
│   └── docx/
├── policies/
│   ├── source-markdown/
│   └── docx/
├── invoices/
│   ├── supplier-invoices.json
│   ├── html/
│   └── pdf/
├── waypoint/
│   ├── invoice-decisions.json
│   └── waypoint-seed.json
└── scenarios/
    └── invoice-assurance-scenarios.json
```

## Authoring posture

Documents start as Markdown so they are easy to review, diff, and maintain. Later, these Markdown files can be converted into `.docx` files for the app to ingest as realistic business artifacts.

Supplier-specific documents must be prefixed with the supplier/customer ID, for example:

- `sup-001-aster-ridge-biomanufacturing-sow.md`
- `sup-002-northstar-fill-finish-quality-agreement.md`

General company policy documents are not prefixed because they apply across suppliers.

## Evidence puzzle design

Contracts and policies should include specific clauses that later invoices can violate. The goal is to showcase Waypoint's ability to interpret contract language, reconcile operational evidence, cite the controlling clause, and draft a supplier response.

Do not put expected findings inside the contract or policy documents themselves. Expected findings should live in separate scenario metadata so the evidence remains realistic.

## Contract source conventions

Each supplier in `suppliers/suppliers.json` should have a corresponding Markdown contract in `contracts/source-markdown/`.

Supplier contracts should stay concise but include 3-5 strong clauses that can drive invoice discrepancies, such as:

- Billability triggers based on QA release, delivery, shipment, milestone acceptance, or regulatory acknowledgement.
- Pricing rules for unit rates, volume tiers, escalation caps, scrap allowances, pass-throughs, storage days, and true-ups.
- Authorization requirements for packaging, route exceptions, rush orders, engineering changes, added countries, or non-standard documentation.
- Evidence obligations for invoice support and dispute response.

## Scenario metadata

Scenario metadata belongs in `scenarios/invoice-assurance-scenarios.json`. It maps future invoice issues to supplier IDs, expected decision states, evidence references, leakage categories, and recommended response actions.

Keep scenario metadata separate from contracts and policies. Contracts and policies should read like normal business documents; scenario metadata can contain expected demo outcomes.

## Invoice seed data

Invoice seed data belongs in `invoices/supplier-invoices.json`. The JSON file is the canonical source of invoice facts for local development, future Postgres seeding, supplier-specific HTML generation, and future PDF generation.

The demo assumes each supplier sends invoice PDFs in its own format. Keep the common reconciliation facts in JSON first, generate supplier-specific HTML invoices from that source, and render those HTML files to PDF. Layout differences should be represented as generation profiles or templates, not as divergent invoice facts.

Supplier-specific invoice templates live in `src/ledgerfield/templates/invoices/`. Use the FastAPI preview app to iterate on styles without changing invoice facts:

```bash
uv run ledgerfield serve
```

Then open `/preview`.

Invoice seed conventions:

- Every supplier should have at least one invoice.
- Invoice line totals must reconcile to the invoice total.
- Most lines should be cleanly matched.
- Roughly 25% of lines should intentionally break a policy or contract rule.
- Non-matched lines should reference `scenario_id` values from `scenarios/invoice-assurance-scenarios.json`.
- Stable supplier billing defaults, such as address, billing contact, tax ID, customer account, and remittance reference, belong in each generation profile's `billing_profile`.
- Transaction-specific invoice document details, such as due date, service period, tax treatment, and support document references, belong in each invoice's `document_metadata`.
- Generated HTML should live under `invoices/html/`.
- Generated PDFs should live under `invoices/pdf/`.

## Waypoint seed export

Waypoint-specific import data lives under `waypoint/`.

- `invoice-decisions.json` is internal Ledgerfield seed metadata for the invoice decision cases Waypoint wants to import.
- `waypoint-seed.json` is generated by `uv run ledgerfield generate-waypoint-seed`.
- The generated payload matches Waypoint's import shape and includes suppliers, contract document references, policies, scenario groups, invoices, nested invoice lines, findings, and evidence references.
- Expected decisions in this folder are app seed metadata, not supplier-facing document content.

## DOCX conversion

Run the Python CLI from the repo root when `.docx` artifacts are needed:

```bash
uv run ledgerfield generate-docx
```

The command writes contract DOCX files to `data/contracts/docx/` and policy DOCX files to `data/policies/docx/`.
